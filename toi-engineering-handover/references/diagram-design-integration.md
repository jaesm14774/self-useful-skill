# 工程交接圖解設計與筆記平台交付

本指南把圖解從「挑一種語法」擴展為完整交付流程：先定義證據支持的意思，再挑語義模式和視覺版型，接著繪製、輸出到目標筆記平台並檢查成品。靈感來自 [Diagram Design](https://github.com/cathrynlavery/diagram-design) 的語義先行、版型分類、少量焦點、輸出尺寸／細節／受眾選擇和圖片匯出方法；TOI 只採用可移植的設計方法，不要求安裝該專案、使用其 HTML 範本或依賴其 CLI。

## 1. 先決定圖要替讀者完成什麼

動筆前先寫一張短的「圖解規格」。它是圖的語義來源，也是把圖源、輸出圖片和程式碼證據對起來的依據。

| 欄位 | 要寫清楚的事 |
| --- | --- |
| 讀者與問題 | 哪位接手者需要用這張圖回答什麼問題？ |
| 核心訊息 | 看三秒後，讀者最需要理解的關係或結論是什麼？ |
| 範圍與層次 | 這是系統脈絡、服務、資料模型、單一情境，還是部署層？圖內節點要維持同一抽象層。 |
| 主路徑 | 從何處開始，經過哪些責任或轉換，最後產生什麼結果？ |
| 節點與責任 | 每個節點代表誰／什麼，實際負責哪件事？ |
| 關係 | 箭頭代表呼叫、資料、事件、相依、控制轉移或人工交接中的哪一種？ |
| 例外 | 哪個拒絕、等待、重試、補償或失敗會改變接手者的判斷？ |
| 證據 | 重要節點、箭頭、條件和邊界各由哪些路徑、符號、規格或營運資料支持？ |
| 待確認 | 哪些地方是推論或未知？要如何在圖上和圖說標明？ |
| 替代文字 | 不能看圖時，讀者仍要知道哪些範圍、方向和主要關係？ |

先檢查圖是否比一段好文字、短表格或例子更能回答問題。若沒有新增理解，就不要為了視覺完整而畫圖。

## 2. 先選語義模式，再選版型

「語義模式」說明這張圖要呈現的行為或風險；「版型」說明資訊如何排在畫面上。同一種版型可表達多種語義，但版型不能替作者決定未經證據支持的系統行為。

| 讀者真正要看懂…… | 語義模式 | 常用版型 | 一定要保留的意思 |
| --- | --- | --- | --- |
| 多個來源爭用有限容量 | 匯流／瓶頸 | 資料流、服務流程 | 來源、等待或容量、受限資源，以及接收和拒絕／延遲結果 |
| 每個階段都要回答相同問題 | 重複階段與固定欄位 | 階段流程、泳道 | 階段順序、固定欄位、空值／不適用狀態和交接 |
| 雜亂輸入如何成為可保存的紀錄 | 非結構化輸入轉成結構化成果 | 資料流、流程圖 | 輸入、轉換、欄位來源、未知值及最終產物 |
| 為何兩個相似請求得到不同決策 | 成對規則追蹤 | 流程圖、比較圖 | 相同規則順序、首次差異、通過／失敗／略過／未到達的區別 |
| 哪些路徑可通過信任邊界 | 安全通道與阻擋路徑 | 架構圖、部署圖 | 信任區、允許／禁止入口、特權關卡、稽核位置 |
| 控制措施在哪裡執行 | 治理／控制目錄 | 分層圖、權限矩陣 | 執行面、負責者、執行時點、覆蓋缺口和例外 |
| 前一層防護失效後剩下什麼風險 | 補償性安全層 | 分層圖 | 每層處理的風險、逃逸限制和最後剩餘風險；不能暗示風險歸零 |
| 系統由哪些可追蹤的子區塊組成 | 可追溯的分解樹 | 樹狀圖、元件圖 | 穩定識別碼、父子關係、輸入／輸出和實作入口 |
| 一個物件經歷哪些階段、等待和終態 | 生命週期 | 狀態圖、階段圖 | 主要階段、等待／重試、取消、成功與失敗終態 |

每張圖只選一個主要語義模式。若兩種模式都必須完整展開，拆成一張總覽和一張細節圖；不要用一個版型硬塞兩種閱讀方向。

## 3. 視覺版型目錄

以下目錄涵蓋 Diagram Design 提供的工程與資料圖型範圍，作為挑選版型的選單，不是每份交接的必做清單。主要交接讀者通常先看 A 類；B 類只有在真實數值、排程、流程量或比較本身就是交接問題時才採用。

### A. 系統、流程與維護

| 版型 | 適合用來回答 | 交接時要特別注意 |
| --- | --- | --- |
| 架構圖 | 元件、責任、邊界和連線如何構成一個系統？ | 交代範圍和一條主路徑；不要和呼叫時序混畫。 |
| 架構差異圖 | 變更前後的拓樸新增、移除、搬移或重接了什麼？ | 兩側用同一範圍和比例，旁邊列出變更清單。 |
| IT 現況圖 | 既有系統如何按部門、區域或現代化階段分布？ | 標出已知現況、待汰換項目和目標狀態的差異。 |
| 流程圖 | 工作如何開始、判斷、成功或失敗？ | 每個決策出口寫條件，保留停止點。 |
| 序列圖 | 多個參與者如何按時間交換訊息？ | 聚焦一個情境；同步回覆、事件、timeout 和重試要分清。 |
| 狀態圖 | 一個物件有哪些狀態與合法轉換？ | 轉換條件與終態要可見；不要用線性步驟替代狀態。 |
| ER／domain 模型 | 業務實體有哪些關係、鍵和資料粒度？ | 使用業務定義和 schema 證據；不要把 ERD 當欄位字典。 |
| Database schema／資料庫結構 | 實體資料表有哪些欄位、SQL 型別、索引、限制和外鍵？ | 依實際 DDL 標示；只列影響查詢、資料品質或維護的欄位。 |
| 時間線 | 哪些事件何時發生、先後為何？ | 標明時區、時間依據和事件來源。 |
| 泳道圖 | 不同人、團隊或系統在哪裡負責和交接？ | 泳道表示責任，不表示部署位置。 |
| Loop／回饋迴圈 | 輸出如何回到前段並改變後續處理？ | 回寫路徑要有明確標籤；不要把普通依賴畫成正向循環。 |
| 巢狀邊界圖 | 元件如何包含在網路、信任或管理範圍內？ | 包含表示範圍，不自動代表內部元件互相連線。 |
| 樹狀圖 | 一個父節點如何拆成多層子責任？ | 樹不能表示多父節點相依或循環。 |
| 組織／責任樹 | 人員、團隊、服務台或升級路徑由誰負責？ | 只列對交接和升級有用的已確認角色。 |
| 分層圖 | 哪些責任屬於不同抽象層、控制面或防護面？ | 層級方向要明確；避免用層數暗示沒有證據的安全保證。 |
| 高階資料平台圖 | 叢集或平台中的端到端資料堆疊有哪些部分？ | 範圍要明確，並拆開讀取、處理、儲存和消費責任。 |
| 多角色處理流程 | 多個階段如何傳遞資料、工作或人工決策？ | 若責任分界是重點，改用泳道。 |
| Medallion／分級資料層 | 各層資料代表什麼品質、保留和存取策略？ | 僅在實際採用該資料分層方式時使用，不把它當通用 ETL 圖。 |
| 角色限定資料流 | 每個資料處理階段由誰執行什麼工作？ | 標出資料和工作責任；不可把角色推測成正式 owner。 |
| 資料平台整合圖 | 來源如何經由平台核心交給消費者？ | 用一致的來源、核心、消費者方向，標示主要協定／邊界。 |
| 權限矩陣 | 每種角色或元件可以讀取、寫入或管理什麼？ | 用「允許／拒絕／未知」文字或符號，不只靠顏色。 |
| 部署圖 | 軟體實際放在哪些環境、節點、區域或網路？ | 只畫已確認的部署和連線；部署不是邏輯架構的替代。 |
| 相依圖 | 哪些元件依賴哪些其他元件，是否有循環？ | 標明箭頭方向；大型圖按維護任務切片。 |
| UML 類別圖 | 類別、操作、繼承和組合如何配合？ | 僅在類別結構直接影響維護任務時使用。 |
| 使用者旅程 | 人在各階段做什麼、遇到什麼摩擦或結果？ | 情緒或滿意度必須有來源；不可將猜測畫成用戶研究。 |
| 服務藍圖 | 使用者可見服務和幕後工作如何跨階段接合？ | 標出可見性界線、前台／後台和支援流程。 |
| 故障魚骨圖 | 哪些成因群組可能導致某項觀察到的結果？ | 只畫已收集或明確待驗證的原因，不把可能原因當根因。 |
| Wardley map | 哪些能力沿價值鏈排列，成熟度如何變化？ | 適用策略或現代化討論；需寫明評估依據與日期。 |
| Kanban | 工作目前在哪個狀態、有哪些阻塞或容量限制？ | 是現況快照；WIP 數量與限制需要有來源和時間點。 |
| 使用者故事地圖 | 任務主幹如何切成版本／交付範圍？ | 適合產品或移轉規劃，不用來描寫已執行的系統流程。 |
| 爆炸軸測圖 | 單一產品或平台有哪些可拆解部件？ | 用於空間或實體結構導覽；抽象軟體邏輯通常不需要立體效果。 |
| 軸測平面圖 | 機房、站點或單層空間如何分區？ | 只在實體位置和走線對維護重要時使用。 |

### B. 數量、風險與比較

| 版型 | 適合用來回答 | 防止誤讀 |
| --- | --- | --- |
| 象限圖 | 方案或風險在兩個有定義的尺度上各在哪裡？ | 解釋軸、範圍與判定方式；不要任意把複雜度壓成四格。 |
| 雷達／蜘蛛圖 | 多個項目在數個可比較指標上如何分布？ | 指標需同尺度且具來源；少數指標改用表格比較。 |
| 極座標圖 | 類別有循環順序且數值大小是重點嗎？ | 類別角度和半徑編碼都要說明，避免暗示數值周期間距。 |
| Venn 圖 | 幾個集合實際有哪些交集？ | 只有交集內容已知且集合數量少時使用。 |
| 金字塔／漏斗 | 層級或轉換過程中數量如何遞減？ | 形狀面積不代表未提供的比例。 |
| 長條圖／Dumbbell | 類別間數量或成對基準與現值差距如何比較？ | 標明單位、期間和完整類別；成對點必須代表同一項目的兩個可比值。 |
| Waterfall／瀑布圖 | 起始值如何由正負項目累積成終值？ | 每個橋接項的計算和起終值可追溯。 |
| Treemap／Marimekko | 數量如何分布在階層或類別 × 系列組合？ | 面積代表哪個數值要明講；極小項目不可無聲消失。 |
| 熱圖 | 多列多欄的每個交叉格值如何不同？ | 色階、缺值和數值範圍須明確；同時提供文字或數字。 |
| 折線與變體（slopegraph、ridgeline、streamgraph、bump） | 連續時間趨勢、兩點斜率、分布或排名變化如何？ | 每種變體有不同語義；不要用線連接無順序的類別。 |
| Gantt／甘特圖 | 任務和階段如何安排在時間軸上？ | 日期、相依、基準或延誤資訊需有證據，不預測未知工期。 |
| 散佈圖／氣泡／蜂群（beeswarm） | 個別項目在兩個變數或分布中的位置如何？ | 說清座標和點大小的意義；避免將相關寫成因果。 |
| Sankey／流向圖 | 數量如何在階段間分流和合流？ | 每條流量使用同一量尺，並核對各節點流入／流出和總數。 |

數值圖表只能表達有資料來源支持的數量。若圖的核心是流程順序，用流程圖；若核心是資源或筆數，才使用流量／統計型圖。

## 4. 建立平靜、可讀的視覺層級

使用者應先看出一條主要訊息，再追讀必要細節。可沿用既有文件、產品或團隊的色彩和字體；沒有既定設計時，從簡單、低噪音的系統開始。

- **一張圖一個主張。** 每個節點代表一項獨立責任；相同責任不要拆成數個裝飾方塊。移除不會改變讀者理解或行動的元素。
- **只突出少數焦點。** 先用中性文字和連線，強調色只留給一至兩個最重要節點、路徑或結果。顏色代表含義時寫明規則，並用形狀、線型或文字作第二線索。
- **用位置表達結構。** 固定一個閱讀方向；同類元件對齊，群組間留白多於群組內。連線盡量走清楚的水平／垂直路徑，避免斜線、交叉、共用接點和穿過非端點方塊。
- **用字體和尺寸表達層級。** 標題、元件名稱、技術副標、箭頭標籤和來源註記各有穩定層級。技術等寬字只用於識別碼、命令、路徑或 schema 名稱；名稱使用易讀的正文樣式，並檢查中文字型 fallback。
- **把長解說移出節點。** 節點名稱保持短；詳細規則放在圖說或相鄰文字。箭頭標出資料、事件、呼叫或條件，不能期待讀者從常見架構猜意義。
- **邊界要有實際含義。** 外框、底色、虛線、圖示和形狀只在表示範圍、信任、非同步或類別時使用；圖例說明無法直接看出的符號。
- **圖示是標籤的輔助。** 只用來快速辨認熟悉的系統角色，不使用裝飾插畫取代責任文字。雲端商標不代表實際採用該服務的證據。
- **圖表不靠互動或動畫才完整。** 最終靜態圖必須有完整標籤、路徑、分支和圖例。若使用互動，只可用於追查細節，不能隱藏重要架構或操作風險。

圖的密度太高時，先刪除重複細節或拆出相連的局部圖；不要縮小字到手機或筆記頁面無法閱讀。架構圖的完整性由已宣告範圍內的重要責任和連線決定，不由節點總數決定。

### 選擇一致的視覺方案

- **清爽淺底**是筆記文件的預設，適合貼進白底頁面、匯出 PDF 和列印。
- **深色底**只在文件本身採深色視覺或讀者明確要求時使用；確認白底檢視或列印時文字與連線仍可辨識。
- **編輯版**可加上短副標、來源／日期帶或少量邊註，適合單獨閱讀的總覽圖；不要把圖中資訊塞進浮動卡片或只在 HTML 頁上可見的效果。

同一份文件可沿用一致的 `paper`（底色）、`ink`（主要文字／連線）、`muted`（次要資訊）、`rule`（界線）、`accent`（焦點）和 `link`（外部互動）語義色角色。具體色碼依目標文件或品牌調整，不照搬參考專案的專屬配色。深淺底、編輯版與尺寸變體都要由同一圖源產生並保持相同事實；無明確需求時，只交一個最適用的變體。動態效果不是必要版型，筆記文件採靜態輸出；只有使用者明確需要互動網頁時才考慮動畫，且第一個靜態畫面仍要完整。

## 5. 為交付目的設定四個選項

| 選項 | 依讀者和目的選擇 |
| --- | --- |
| 格式 | 可在 Markdown／Notion 編輯的 Mermaid、draw.io 原始檔、SVG、PNG；只有在使用者明確要網站或互動展演時才把 HTML 當主要交付。 |
| 尺寸 | 筆記頁內嵌、寬版頁面、簡報或列印。先依正常顯示寬度安排文字大小，再輸出；不要先做大圖後整張縮小。 |
| 細節 | 精簡總覽、平衡導覽、忠實細節。精簡只能拿掉不影響主問題的資料；不可省略會改變責任、安全、非同步或恢復方式的關係。 |
| 讀者 | 新維護者、值班人員、支援／業務夥伴、主管。改變術語密度和說明方式，不改變系統事實。 |

每張圖採用最適合問題的一種主版型。若比較不同版型，先向讀者說明每種版型各自呈現什麼，不要默默重排成另一種語義。

## 6. Notion 與 Markdown 筆記文件的預設交付

筆記平台的正文以 Markdown 友善的標題、段落、簡短清單和連結為主；在架構首次被解釋的位置放圖，並在圖的前後寫清楚範圍、閱讀方向、重要例外和程式碼證據。不要將整份交接包成只在瀏覽器開啟的 HTML 頁面。

### 可直接放進 Notion 的做法

1. 將交接正文整理為 `handover.md`。Markdown 版本保留章節階層、可查找文字、相對路徑和來源連結，作為筆記頁匯入／貼上的正文底稿。Notion 的 Markdown 匯入不會可靠保留標題錨點；多頁交接匯入後，請用 Notion 原生頁面連結或目錄重建閱讀導覽，並逐頁測試連結。保留在版本庫中可用的 Markdown 連結，不代表匯入後的 Notion 導覽已驗證；細節見[Notion Markdown 匯入限制](https://www.notion.com/help/import-data-into-notion)。
2. 為每張需閱讀的圖產生同名 SVG 和 PNG。SVG 保留向量品質；PNG 是容易在各裝置預覽及上傳的備用／分享圖。Notion 官方文件列出兩者為支援的圖檔格式。
3. 在 Notion 正文預留圖的位置，建立 Image 區塊並上傳 SVG 或 PNG；設定簡短的替代文字，並用圖說標明圖名與來源。不要假設本機相對 Markdown 圖片路徑已成為 Notion 的雲端圖片。
4. 保留一份唯一可編輯圖源：簡單圖用 `.mmd`／Mermaid，精確排版用 `.drawio`，直接繪製的向量圖保留 `.svg`。PNG／SVG 是由圖源輸出的交付版本，更新時一起重新輸出，不能手改圖片後讓原始圖源過期。
5. 若選 Mermaid 作為 Notion 內的原生呈現，在頁面建立 Code 區塊、貼上 Mermaid 原始碼，將語言設成 Mermaid，再選 Preview 或 Split。Notion 的 Mermaid 預覽依目前支援語法工作；不支援的語法則使用已輸出的 SVG／PNG 圖片。
6. 將可編輯來源放在程式碼儲存庫的文件資料夾，或以 File 區塊附在筆記頁。正文附近提供來源路徑、版本／commit、圖的證據範圍和負責維護角色。

這個交付保留兩種讀法：筆記頁中的圖片讓讀者直接看清完整架構；旁邊的 Mermaid 區塊或附檔讓維護者能追查並修改圖源。若只交 Markdown 圖片語法或只交未渲染 Mermaid 原始碼，先確認目的平台確實能顯示圖，再視為完成。

### 建議的檔案組織

```text
handover/
  handover.md
  figures/
    01-system-context.png
    01-system-context.svg
    02-request-flow.png
    02-request-flow.svg
  diagrams/
    01-system-context.mmd
    02-request-flow.drawio
```

若文件與程式碼儲存庫同版控，正文的圖像連結可用 `figures/01-system-context.png`，原始圖源放 `diagrams/`；匯入 Notion 時另外上傳圖片，並把圖源作為 Mermaid 區塊或附檔。若平台可透過權限穩定存取版本庫的圖片，可使用已驗證的連結；不要使用會過期的臨時 URL。

在文件圖像附近放一段簡短圖說：

> **這張圖回答：** [系統範圍／讀者問題]。**如何讀：** [主路徑與閱讀方向]。**圖源與證據：** [圖源路徑、版本／commit 和主要程式／規格線索]。**替代文字：** [不能看圖時仍需知道的主要責任、方向和關係]。

## 7. 繪製、匯出和走讀

1. **先完成圖解規格。** 用程式碼、設定、測試、規格或可信營運來源確認責任和箭頭。保留事實、推論和未知三種狀態。
2. **選語義模式和版型。** 先問行為是容量、階段、政策、信任、控制、補償或生命週期，再從目錄挑最清楚的結構。不要只因為某個版型新穎就採用。
3. **決定四個交付選項。** 設定格式、閱讀寬度、細節密度和目標讀者；如果輸出筆記平台圖，SVG／PNG 和唯一可編輯圖源列入交付。
4. **安排閱讀方向與視覺重點。** 先放主路徑、邊界和結果，再加一條會改變維護者行動的例外。讓重要出口在靜態畫面可辨識；圖例、標題、來源和日期放在不遮住路徑的位置。
5. **產生圖源與目標格式。** 優先沿用程式碼儲存庫已有的圖表工具。若重繪 Mermaid、draw.io／diagrams.net 或 Excalidraw 等既有來源，保留原有事實和關係，只調整版面與視覺層級；解析器或匯出器不能替架構事實背書。
6. **在目標文件檢查圖片。** 開啟 SVG／PNG 在實際筆記寬度和手機窄寬下檢視；確認標籤可讀、沒有裁切、箭頭清楚、圖例仍在、文字沒有只靠顏色辨認。將最終圖放進一份試貼／預覽頁後再調整。
7. **比對圖和來源。** 確認圖源、渲染圖、圖說和程式碼證據描述同一版本、同一邊界與相同箭頭語義。圖源解析、圖片成功輸出、筆記平台實際顯示和非作者走讀是四種不同檢查。
8. **記錄尚未完成的檢查。** 沒有可用的平台預覽或未安排非作者走讀時，清楚寫出未驗證範圍；不要把 SVG／PNG 匯出成功說成 Notion 畫面或使用者理解已通過。

## 8. 完稿檢查清單

- [ ] 圖回答一個明確的接手者問題，且圖上每個節點和關係都有用途。
- [ ] 主要路徑和範圍完整；同步、非同步、資料、控制、失敗與信任界線沒有被混成一種箭頭。
- [ ] 圖中每個事實有對應程式碼／文件證據；推論和未知有清楚標記。
- [ ] 閱讀方向一致，箭頭與標籤不遮疊，無裁切或不必要交叉；若過密已拆圖。
- [ ] 顏色、線型、形狀、圖示和圖例相互一致，且色彩不是唯一語義載體。
- [ ] Notion 頁面已插入實際 SVG／PNG 並填寫替代文字，或已確認原生 Mermaid 預覽，且在目標寬度檢視。
- [ ] 編輯來源可找到，圖片由同一來源產生；圖說提供替代文字、路徑與版本線索。
- [ ] 未驗證的語法、平台畫面、正式環境行為或讀者走讀沒有被寫成已驗證。
