# TOI — 把系統交代給下一個人

交接文件是寫給下一個要接手的人。從他正在幫誰維持什麼結果開始，帶他走過一個真實情境，再說明系統如何做到、出問題時去哪裡看，以及什麼情況需要停下來找人。程式碼和架構是解釋的證據與路標；它們要幫讀者理解工作，不要讓人獨自從檔名和方塊猜出故事。

## 何時使用

- 新維護者、值班人員、支援或跨團隊夥伴要接手服務、資料流程、平台或程式庫。
- 現有文件沒能讓接手者說清楚系統為誰解決什麼問題，或不知道如何開始、觀察和求助。
- 需要依程式碼與營運證據審閱或改善交接指南。

若需求只涵蓋一個 API、函式或操作步驟，直接更新對應文件；若已有入口指南，優先補足它並連到細節。

## 工作方式

1. **先理解接手者的處境。** 寫下誰會讀、他為何現在需要這份文件、已熟悉什麼、讀完要能做什麼。入口先回答：系統替誰完成什麼工作、出錯的影響、讀者現在能安全做的第一步，以及本文件適用的範圍和版本。
2. **把程式碼當證據來查。** 依序檢查現有文件、規格、業務規則、程式、設定、測試、部署和維運線索；適用時再核對正式環境、事故紀錄或負責角色。保留既有工作目錄變更。每個重要說法都能回到來源；程式碼和測試只能支持它們實際證明的範圍。分清楚已觀察事實、程式推論和待確認事項。
3. **用一個人熟悉的真實情境帶路。** 選一筆請求、一個資料批次、一項使用者任務或一次常見故障。先交代發生了什麼、系統要保護哪個結果，再按先後說明規則、狀態變化、成功／失敗訊號和接手者下一步。技術細節貼在它解釋的那一步旁邊，連到實際檔案或操作資料。
4. **替每個問題選清楚的說法。** 看內容選用小型例子、概念比喻、流程／時間線、責任地圖、狀態圖、標註畫面或短表格。比喻要對應真實機制，並指出它不適用的地方；圖表需有白話標題、帶讀文字和證據連結。不要只交出框框、箭頭、目錄樹或術語表。
5. **依需要逐步揭露細節。** 先給方向和一條主線，再介紹讀者此刻需要的概念、系統責任、實際程式位置與維護細節。架構圖用來回答主線中尚未理解的責任或邊界問題；程式碼導覽用來幫人找到下一步，不以檔案順序當成整篇故事。
6. **寫出安全的下一步。** 每項操作交代前提、入口、預期結果和確認方式。故障解說沿「看到什麼 → 先查哪個訊號 → 如何分辨 → 已核准的處理／復原 → 何時停止並升級」展開。正式環境操作連到已驗證的維運操作手冊（runbook），不自行編造命令；權限和秘密指向核准流程。
7. **請接手者試著走一次。** 讓未參與撰寫的人依文件說明一條情境、找到觀察點並完成一項安全的代表性任務。記下卡住的地方並修正；若尚未走讀，明確標示未驗證。列出文件負責角色、適用版本／日期、未解問題和後續知識移轉安排。

研究從證據開始，文件從人的問題開始。章節順序依接手者要完成的工作安排；完整度由風險與讀者任務決定，無須為填滿固定章節而重複內容。

## 寫作界線

- 讀者可以是工程師、值班人員、支援、產品或資料夥伴；依實際讀者調整詞彙和細節，不假設每個人已熟悉此專案。
- 先講一個具體情況和它的重要性，再介紹名詞、縮寫和程式名稱。第一次出現的必要術語，用一句白話說明它在此情境代表什麼。
- 重要段落回答「發生什麼事、為什麼在意、系統如何處理、我去哪裡確認」。一次只解釋一個主要意思，使用讀者能採取的動詞和可觀察結果。
- 例如，「Scheduler → Worker → Redis → S3」這串名稱需要由情境和責任說明帶讀：某位使用者何時會看到什麼結果、哪些步驟負責等待／處理／保存、旁邊有哪些可觀察訊號與程式入口。這只是寫法示意；實際說明必須依目標程式碼儲存庫查證。
- 圖、文字、操作步驟和證據連結需互相吻合。圖說要帶讀主要路徑；圖片提供替代文字或等效說明；寬表只用於確實需要逐項比較的資訊。
- 交接指南說明系統如何服務人、接手者怎麼開始和去哪裡求助；具體操作步驟由正式維運操作手冊（runbook）承載。交接指南也不代表即時監控或正式環境驗證。未知處保留目前已知內容，寫明影響、確認來源和確認前的安全做法。
- 不放憑證、個資或秘密；存取需求連到核准申請途徑。

## 使用範例

- 「請依這個程式碼儲存庫的證據寫一份新維護者上手指南。從使用者遇到的問題開始，帶我走過一條真實流程，再連到規則、程式位置、觀察訊號和安全的第一步。」
- 「請檢查這份交接文件，找出不熟悉系統的人會卡住的地方；把程式架構說明改成能回答實際任務的白話解說，保留證據和未知事項。」
- 「請用一個真實例子說明資料怎麼變成報表，搭配適合的流程圖、短例子和程式入口；不要把程式碼儲存庫中的目錄逐一改寫成正文。」
- 「請用讀者看得懂的方式說明故障第一步和升級邊界，並確認所有正式操作都連到已驗證的維運操作手冊。」
