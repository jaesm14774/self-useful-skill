# 用圖和版面帶人看懂系統

本指南協助作者挑選讀者容易理解的表達方式，並讓交接文件可以快速定位、跟著情境走、按需查深。讀者需要理解因果時，可能是短故事或例子；需要看順序、狀態、責任或空間關係時，再評估圖是否更清楚；精確比較欄位時，表格可能更好。圖型選擇見[圖型選擇與繪製手冊](diagram-selection.md)；只有當讀者需要了解系統範圍和外部依賴時，才使用[架構總覽指南](architecture-overview.md)。

## 視覺優先與圖的配置

- 寫主要章節前先問讀者的疑問，再選最簡單的表達方式。要建立情境與因果，可先給一個小故事或具體例子；要看順序、關係或選擇時，可用時間線、流程、責任圖或其他對應視覺。
- 預設讀者沒有專案或 domain 背景。先用白話交代人的問題、系統承諾、重要名詞和成功結果，再讓讀者接觸元件名、檔名或縮寫；圖不能代替這段教學。
- 不要求所有交接都包含相同圖表。先用一個能說明系統價值的情境作為主線，再按讀者是否需要理解範圍／外部依賴、狀態或跨角色責任，決定是否加入架構圖、流程圖或其他視角。
- 把重要圖或例子放在它解釋的段落旁。每張圖搭配白話標題、如何閱讀的短說明和來源；文件平台不支援圖源時，輸出並嵌入可讀的 SVG／PNG。
- 只在精確欄位、數值、逐項屬性或固定條件比較較重要時優先用表格。若表格是在表達誰接誰、先後怎麼走、狀態怎麼轉或在哪裡跨邊界，通常再補一張圖會更容易理解。
- 要說明畫面操作、特定儀表板或設定位置時，加入真實且有標註的截圖；標出入口、關鍵區域和預期訊號。每張截圖遮蔽秘密與個資，標明適用版本／環境，旁邊仍提供步驟文字，避免讀者只靠過期畫面操作。
- 表達方式以「能否加快理解」決定，不以圖表數量裝飾文件。讀者需反覆讀才能理解一個步驟時，可改寫故事、補例子或畫局部圖，保留必要的白話解說。

## 先決定問題，再選圖

每張圖先寫下一句問題與目標讀者，例如「新維護者要知道資料從哪來、會流經哪些責任邊界，才能開始追一筆失敗工作」。再選能回答問題的圖型。完整圖型對照、適用情境與 Mermaid 起手式見[圖型選擇與繪製手冊](diagram-selection.md)；以下是常見起點：

| 讀者問題 | 圖型 | 圖上應突顯 |
| --- | --- | --- |
| 使用者在什麼情境需要這個結果？ | 一分鐘情境／具體例子 | 人物、期待、系統承諾、重要條件和結果 |
| 系統為何存在，跟使用者或外部系統怎麼互動？ | 系統脈絡圖（有助尋路時） | 使用者、系統邊界、外部依賴及主要互動 |
| 系統由哪些可部署或負責不同工作的單元組成？ | 容器／服務架構圖 | 主要元件、責任、資料存放和技術邊界 |
| 一筆工作或資料如何流過系統？ | 資料流／業務流程圖 | 起點、轉換、狀態、分支、結果與失敗路徑 |
| 某個重要操作按照什麼先後順序發生？ | 序列圖 | 參與者、呼叫方向、同步／非同步交接、錯誤或重試 |
| 元件實際部署在哪，操作邊界在哪？ | 部署／環境圖 | 執行環境、網路／信任邊界、平台服務與運作責任 |
| 重要資料代表什麼、如何關聯？ | ERD／資料模型圖 | 實體含義、粒度、鍵、基數及時間欄位意義 |

C4 適合表達軟體的靜態結構和不同縮放層次；商業流程、狀態、資料模型或特定時序通常應搭配對應圖型，不要硬塞進一張結構圖。複雜圖應拆成同一抽象層的數張圖，並以連結說明彼此關係。

推薦依讀者理解順序逐層揭露：**人的情境 → 系統如何回應 → 為何這個判斷重要 → 需要時查看系統邊界、程式位置和操作細節**。讀者若要先確認系統範圍和外部依賴，可先給系統脈絡；不需要把所有層次都畫出來。

## 圖表的清楚與一致

- 標出標題、讀者要回答的問題、系統範圍、更新或驗證日期、圖例，以及必要的來源／revision。讓讀者知道它是全貌還是某一條路徑的局部圖。
- 一個方塊代表一個穩定且可命名的責任；名稱使用「業務角色＋必要技術名」，避免將產品名、function、table 和團隊名放在同一層而沒有區別。
- 每條箭頭都寫上實際交換的資訊或觸發原因；適用時標示協定、資料形式、同步／非同步或批次頻率。方向有意義時使用清楚單向箭頭，避免未解釋的雙向箭頭。
- 一張圖維持一致的形狀、線型和顏色語意；畫出系統、外部服務、資料儲存和信任／責任邊界。圖例少而精，線條交叉能避免就避免。
- 以排列、群組、留白、標題和線型建立視覺層次。用色彩輔助辨識，不讓色彩成為唯一差異；注意對比和黑白列印時仍可辨識。
- 只保留回答問題所需的元件。若圖上的每個箭頭都需長段解釋才能理解，就拆圖或改用步驟敘述。
- 圖旁加上文字，說明重要路徑、正常結果、主要例外，以及接手者應回到哪些程式／設定檢視。圖上概念要連到程式碼儲存庫中的實際名稱或穩定連結。
- 將可維護的圖源與文件一起版控。簡單流程可用 Mermaid；需要精確排版或複雜連接時可用 Draw.io 等繪圖工具，同時保留可編輯原始檔。使用程式碼儲存庫已採用的工具時沿用既有慣例。
- 在最終文件檢查實際渲染，確認文字沒有裁切、縮得太小、跨頁斷裂或圖例被分離；圖若無法正常顯示，應有 caption 或等效文字替代。

Azure Well-Architected 的圖表指引建議依受眾和溝通目的選圖、使用一致且明確的符號／流向、標示範圍與 metadata，並考慮可讀性與無障礙。GitLab 文件指引偏好簡單圖使用 Mermaid，也說明較複雜圖可用 Draw.io 並保留編輯來源。

## 文件版面與閱讀節奏

### 先讓讀者找到方向，再逐層展開

把頁面安排成三種閱讀深度，讓接手者可以先定位、再理解、最後按需查細節：

1. **一眼定位：** 標題說明系統結果或讀者任務。首屏用短段落交代誰需要什麼、系統交付什麼、文件涵蓋範圍與第一個安全入口；文件負責角色、適用版本／環境和最後核對日期以精簡資訊列呈現。先讓讀者知道要不要繼續看，不先放元件清單、程式碼或大張欄位表。
2. **跟完一條主線：** 選一筆批次、資料記錄或使用者任務，照實際順序從觸發帶到下游結果。資料流程可沿「來源與觸發 → 會改變結果的判斷／轉換 → 交付位置與使用者 → 完成、新鮮度或異常訊號」展開；每一階段用白話回答發生什麼、為何重要、如何確認，再附最少的證據入口。正常路徑先保持連續；全量／增量等策略、例外與不同責任用清楚的分支或獨立小節說明。
3. **按任務深入：** 讓讀者從「追一筆延遲資料」「確認哪種更新策略適用」等入口找到操作、診斷和技術參考。先給選擇條件或步驟，再給對應程式、設定、欄位或正式操作文件。精確內容可以放子頁或附錄，但要在正文說明何時需要它，不能要求讀者自行從參考資料拼回主流程。

每一步可沿用一致的小節節奏：**發生什麼 → 為何影響結果 → 怎麼確認 → 要深入時看哪裡**。並非每一步都要填四個標籤；讀者已能理解時就直接敘述，避免把內容寫成格式僵硬的表單。

### 先安排讀者理解順序，再選版型

- 長篇交接依任務採「入口定位 → 一個真實情境 → 重要規則與影響 → 系統和程式線索 → 操作與故障 → 限制和參考」的閱讀路徑。需要快速掃讀的摘要可放第一屏；各段仍連成一個完整故事。
- 先寫一份精簡內容骨架：標題直接說明問題或任務，開頭交代誰要完成什麼，每節回答一個讀者問題，再補例子、證據和維護影響。骨架是安排閱讀順序，不是壓縮交付內容；寫完後依[交接方法的覆蓋盤點](handover-method.md#先盤點完整度再安排章節)補足每個適用主題。若內容太長，拆成互相連結的 Markdown／筆記頁面，摘要保留導航用途。
- 一張圖或一節文字只承擔一個主要問題。若要同時說明部署位置、呼叫順序和資料狀態，就拆成互相連結的視角，而不是加更多圖例或把字縮小。
- 將複雜內容拆成「主路徑／概念圖 + 例外說明 + 精確 reference」；讀者先取得整體模型，需要時再查門檻、欄位、命令或完整條件。
- 讓文件本身像清楚的產品介面：第一屏提供定位和下一步，導航沿用讀者會說的任務名稱，內容依「先理解、再操作、最後查細節」漸進展開。挑選版面時可先看[交接呈現模式庫](presentation-pattern-library.md)，以讀者問題和可用證據決定模式。

### 把交接文件當成可探索的介面

- 長篇文件先做「接手起點」：用一句話說明人遇到什麼問題、系統交付什麼結果，並讓讀者立即找到適用範圍、更新日期、負責角色、第一項安全任務和相關章節。
- 導航項目用任務語言，例如「追一筆延遲資料」或「確認部署設定」，避免只用抽象章名。不同角色有不同入口時，提供角色／情境捷徑，但仍共用同一份已核對的事實。
- 將標題、摘要、視覺圖、說明和來源排成同一段閱讀路徑。圖旁指出主路徑與會改變行動的分支；證據連結靠近它支持的句子，讓讀者不用在附錄中猜來源。
- 只有在文件夠長或章節夠多時才加入站內搜尋、篩選、索引或折疊。搜尋失敗時仍能沿目錄找到內容；折疊區塊不得藏住主要安全條件、系統邊界或未確認風險。
- HTML／網站介面採用回應式單欄閱讀、清楚的焦點順序、可見鍵盤焦點、語意化標題和足夠對比；列印時保留重要連結、圖例和來源。互動內容需有文字等價內容，動畫預設簡短或關閉，並尊重減少動態效果的偏好。
- 若輸出是 Markdown、Word 或其他靜態文件，優先使用該格式穩定支援的標題、錨點、圖像、提示區塊和連結。不要為了「像網站」而把內容切成失去上下文的卡片，或引入儲存庫沒有的前端依賴。
- 若交接要放進 Notion，Markdown 是正文底稿，架構圖需另外以 Notion 圖片區塊插入 SVG／PNG，並保留一份可編輯圖源。簡單 Mermaid 圖可在 Notion 的 Code 區塊中選 Mermaid 並切換 Preview／Split；要保留精確排版或完整架構時，圖片是主閱讀版本，圖源放在同一頁的檔案區塊或連到版本庫。匯入 Markdown 不代表本機相對圖片路徑或 Mermaid 原始碼已成為 Notion 的可視圖表。詳見[圖解設計與筆記平台交付指南](diagram-design-integration.md)。
- 讀者尚未熟悉圖型名稱時，先讓他看一個短預覽和白話用途，再給圖型名稱。若需比較版型，可提供小型模式選單；使用者選擇和備註一旦提供，就只將選定模式套用到指定章節。

「Answer me with HTML」先寫 Markdown 草稿，再交給排版工具安排圖表位置；這個分工讓作者把時間用在事實、關係和解說上。TOI 可沿用程式碼儲存庫已有的 Mermaid、Draw.io 或互動圖工具，並持續使用現有文件格式。[專案方法](https://github.com/QingYunA/answer-me-with-html#how-it-works)

### 建議的入口頁

長篇交接文件在第一屏回答：

- **文件用途**：誰要讀、為什麼現在交接、涵蓋哪些服務或流程。
- **系統摘要**：一兩段白話說清楚讀者／使用者遇到的情況、系統承諾和結果。
- **讀完能做什麼**：接手者的具體任務或能力。
- **可信度資訊**：負責人／團隊、最後驗證日期、適用版本或環境，以及未解項目的位置。
- **閱讀索引**：把 domain、架構、開發／部署、日常操作、故障處理與已知風險連到各自章節。

對資料工程交接，入口可再明確標出主要來源／觸發、結果落點或消費者，以及讀者何時應預期資料可用。只有在這些資訊已查證且會改變接手者理解時才呈現；不用為了填滿固定欄位猜測排程或 SLA。首屏可用短段落搭配一行 metadata 和少量任務連結，不必把上述資訊塞進寬表。

### 中大型交接以入口帶讀者走進多頁內容

入口頁先解釋系統為誰工作、主要能力、核心業務情境、適用版本和第一條閱讀路徑，再將需要深入的內容分頁。不要讓剛接手的人從一排檔名猜哪頁重要。

按讀者要完成的工作拆頁，而不是按 repository 目錄或每個模組拆頁。常見分法是：

- **背景與 domain：** 說明人、業務物件、重要定義、規則、例子和影響。
- **核心流程與架構：** 把一條主要情境走完，配上能解釋責任、資料去向和外部邊界的圖。
- **操作與變更：** 告訴接手者如何上手、看成功訊號、處理安全的日常工作、追查影響並前往正式 runbook。
- **精確參考：** 連到已存在的規格、資料字典、API 或操作手冊，說明何時以及在哪個環境使用。

入口索引應描述每頁回答的問題，連到已建立且有內容的頁面；每個子頁保留版本／範圍、短定位和回到入口的連結。檔案路徑只作為必要的證據或下一步線索：不要逐檔加註、不要列出所有 repository 檔案，也不要要求讀者閱讀程式碼才能補上交接正文缺少的背景。

### 讓頁面容易掃描

- 先列大綱再寫長文。H1 聚焦系統或接手任務，H2 用讀者會問的問題或要做的工作，H3 用於主流程步驟、策略差異或重要例外；標題寫明該節答案，不用「背景」「細節」等空泛字眼，也避免過深層級。
- 長文件提供目錄和章節錨點；讓摘要、圖和關鍵任務容易找到。內容按理解順序排列，細節可連到次級參考文件。
- 重要結論和第一個行動放前面。每段集中一個意思，搭配留白、短段落、清單和小節避免大面積文字牆。
- 清單使用平行語法；表格只在讀者需要比較多個屬性時使用。表格前先說清楚比較目的，欄位簡短，避免把多段說明塞入儲存格。
- 程式碼區塊只保留完成一個目標所需的最小範例，清楚標示語言、檔案／命令用途和執行後的預期觀察；不要貼整支模組後要求接手者自行解讀。
- 在術語第一次影響理解時解釋。陌生 acronym 第一次拼出全名並寫白話含義；避免只出現一次的縮寫。
- 採一致的色彩、字體層級、圖說和提示樣式；「結果」「如何確認」「停止／升級」等提示用詞固定且可掃描。色彩只能輔助，必要條件須在文字中可讀。以單欄敘事為主，寬表或多欄只在比較需要時使用，並檢查手機和窄視窗的閱讀情況。
- 在原始章節解釋原因和因果；reference 頁可用於精確查找。將教學、任務操作、查詢資訊和背景說明連結到適合的位置，而非重複抄寫。
- 用可驗證的短句寫圖說：**這張圖回答什麼 → 沿哪條主路徑讀 → 哪個分支會改變維護者動作 → 回到程式碼儲存庫的哪裡核對**。圖上節點不必逐一複述，但關鍵因果和責任要說清楚。
- 優先用主動動詞和一致名詞；把「由元件處理」改成實際責任者與動作。將多個條件、例外或限制拆成有順序的句子或清單，保留門檻、時間範圍、前提和例外，不為了追求短句而刪掉精度。
- 自動寫作 lint 可提示長句、被動語態、冗詞、術語不一致和過長段落；把它當成修稿線索，不當作技術正確性判定。程式名稱、引用、門檻和 domain 語義要由作者按證據確認。

### 交付前快速檢視

以接手者而非作者的角度檢查：

1. 不先讀程式，是否能先說出系統為誰解決什麼問題？
2. 不先問作者，是否能解釋一個重要 domain 概念或規則如何影響結果？
3. 能否沿著一條主線或連結頁追完真實路徑，知道責任、成功訊號和失敗時去哪裡？
4. 入口能否讓人知道每個子頁回答什麼，所有連結是否有效且可存取？
5. 圖上的用語是否能在程式碼儲存庫或文件中找到對應？
6. 版面是否讓人先理解再查細節；是否避免過長表格、逐檔註釋、未解釋縮寫和無解說程式碼？
7. 文件是否指出最後驗證時間、適用 commit／版本、待確認的事實和維護 owner？
8. 只讀首屏和主流程，接手者能否指出資料從哪裡來、怎麼交付，以及如何判斷結果已可使用？
9. 在實際目標平台的窄視窗中，標題、圖、表格和錨點是否仍然可讀、可用？
