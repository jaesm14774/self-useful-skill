# TOI — 把系統交代給下一個人

交接文件是寫給下一個要接手的人；預設他沒有這個專案的背景或業務領域（domain）知識。先說明人遇到什麼問題、為何重要、系統承諾交付什麼結果，再用一個真實情境教他理解關鍵概念和流程，最後帶到架構、操作與維護細節。程式碼和架構是解釋的證據與路標；它們要幫讀者理解工作，不要讓人獨自從檔名和方塊猜出故事。

## 何時使用

- 新維護者、值班人員、支援或跨團隊夥伴要接手服務、資料流程、平台或程式庫。
- 現有文件沒能讓接手者說清楚系統為誰解決什麼問題，或不知道如何開始、觀察和求助。
- 需要依程式碼與營運證據審閱或改善交接指南。

若需求只涵蓋一個 API、函式或操作步驟，直接更新對應文件；若已有入口指南，優先補足它並連到細節。

## 工作方式

1. **先理解接手者的處境。** 寫下誰會讀、他為何現在需要這份文件、已熟悉什麼、讀完要能做什麼。預設讀者不懂專案內部縮寫、業務流程和元件分工；先教會他理解問題與結果，再介紹專有名詞。入口先回答：系統替誰完成什麼工作、出錯的影響、讀者現在能安全做的第一步，以及本文件適用的範圍和版本。
2. **固定證據版本，辨認系統核心。** 以使用者指定的 tag、release 或 commit 為準；未指定時，以目前 checkout 的 HEAD 作為交接基線。預設忽略所有未提交和未追蹤檔案：不讀其差異、不把它們當證據、不列入圖表或文件，也不在交接內容提及。這項範圍規則與保護工作目錄是兩件事。接著先從使用者結果、主要能力、端到端流程、業務判斷、資料契約和系統邊界辨認核心，再查文件、規格、程式、設定、測試、部署和維運線索；不要用檔案數量或目錄結構代替核心判斷。每個重要說法都能回到來源；程式碼和測試只能支持它們實際證明的範圍。分清楚已觀察事實、程式推論和待確認事項。
3. **用一個人熟悉的真實情境帶路。** 選一筆請求、一個資料批次、一項使用者任務或一次常見故障。先交代發生了什麼、系統要保護哪個結果，再按先後說明規則、狀態變化、成功／失敗訊號和接手者下一步。技術細節貼在它解釋的那一步旁邊，連到實際檔案或操作資料。
4. **先安排讀者怎麼讀，再放技術線索。** 依[視覺與文件設計指南](references/visual-document-design.md)安排首屏、層級和版面：
   - **入口：** 先讓讀者一眼看懂誰需要什麼結果、系統交付什麼、適用範圍和第一步。
   - **主線：** 沿一條代表情境從開始走到結果。資料工程交接通常依序交代資料來源／觸發、會改變結果的判斷或轉換、交付位置／使用者，以及新鮮度、成功或異常訊號。
   - **分流：** 不同處理策略先說明怎麼選，再各自描述結果與例外；不要把不同路徑混成一長串步驟。
   - **深入查找：** 每一階段先用白話說發生什麼與為何重要，再補可觀察訊號和精確來源。程式、產品名和縮寫放在它們解釋的步驟旁。看讀者的問題選用例子、流程／時間線、責任地圖、狀態圖、標註畫面或短表格；跨服務用圖交代責任，小型元件依需要省略。比喻要對應真實機制並指出邊界；圖表要有白話標題、帶讀文字和證據連結。
5. **依主線調研、規劃大綱，再分工撰寫。** 先由交接負責人查清楚讀者、使用者結果、主要端到端情境、domain 規則、系統責任和證據來源；用這條主線和覆蓋盤點規劃入口及各頁大綱，再決定哪些邊界清楚的頁面適合平行委派。可用且適合時，依[交接方法](references/handover-method.md)為 subagent 設定分工合約，並由主編負責整合、查證、統一敘事與完成索引。先規劃索引和閱讀地圖；各頁有實質內容後再完成索引連結。依讀者任務拆成互相連結的背景與業務規則、核心流程與架構、操作與變更等頁面；索引要說明每頁回答什麼，不能代替正文。架構圖用來回答主線中尚未理解的責任或邊界問題；程式碼導覽用來幫人找到下一步，不以檔案順序當成整篇故事。繪圖時先確定要表達的行為或關係，再選版型和輸出格式；若文件要放進 Notion 或其他筆記平台，提供可直接插入的 SVG／PNG 和可追溯、可修改的原始圖源，不把 HTML 當成必要交付物。依[工程交接圖解設計與筆記平台交付指南](references/diagram-design-integration.md)處理。
6. **寫出安全的下一步。** 每項操作交代前提、入口、預期結果和確認方式。故障解說沿「看到什麼 → 先查哪個訊號 → 如何分辨 → 已核准的處理／復原 → 何時停止並升級」展開。正式環境操作連到已驗證的維運操作手冊（runbook），不自行編造命令；權限和秘密指向核准流程。
7. **逐項驗收完整度並交付可讀文件。** 依[交接方法](references/handover-method.md)的覆蓋盤點，確認每個適用範圍都有正文解答、可用的正式文件承接，或明確列為待確認；不適用項目要說明原因。重要工作流程要交代觸發、判斷、結果、例外、觀察方式和安全下一步。完整交接以可實際開啟的 Markdown／筆記頁面交付；長內容拆成有共同入口、索引和交叉連結的多頁文件。不要只回傳摘要、目錄或尚未建立的延伸文件，也不要為了單次回覆長度把必要內容刪掉；若需分批，逐批完成文件並確認覆蓋後再回報。
8. **請接手者試著走一次並如實標示狀態。**
   - 先寫讀者驗收情境：`User` 是剛接手的維護者；`Given` 他只先看入口；`When` 他沿一筆代表性資料或任務追到結果；`Then` 他能說明用途、主要判斷、成功訊號和下一步。
   - 讓未參與撰寫的人依文件完成這條情境、找到觀察點並試做一項安全任務；記下卡點並修正。若尚未走讀，明確標示未驗證。
   - 回報交付頁面、覆蓋範圍、未解問題、走讀狀態、文件負責角色、適用版本／日期和後續知識移轉安排。覆蓋完整、未知事項已揭露、但尚未走讀時，標示「覆蓋已完成，讀者驗收待進行」；若未知事項使接手者無法安全執行關鍵工作，標示「交接待補」，不要稱為完整驗收。

研究從證據開始，文件從人的問題開始。章節順序依接手者要完成的工作安排，不必使用固定章名；但「不採固定章節」不等於省略適用範圍。完整交接可以有明確的待確認事項，不能把尚未查證或尚未撰寫的內容藏在短摘要裡。沒有固定字數門檻；依讀者能否安全接手和覆蓋盤點判定完整度。若單次輸出或上下文容量不足，分頁寫入可交付文件並提供索引，逐頁完成後再報告尚未驗證項目。

## 寫作界線

- 讀者可以是工程師、值班人員、支援、產品或資料夥伴；依實際讀者調整詞彙和細節，不假設每個人已熟悉此專案。
- 先講一個具體情況和它的重要性，再介紹名詞、縮寫和程式名稱。第一次出現的必要術語，用一句白話說明它在此情境代表什麼。
- 重要段落回答「發生什麼事、為什麼在意、系統如何處理、我去哪裡確認」。一次只解釋一個主要意思，使用讀者能採取的動詞和可觀察結果。
- 先補足接手所需的背景：誰使用系統、沒有系統時會怎樣、核心業務物件和規則代表什麼、成功結果長什麼樣。不要把這些知識留給讀者從程式或術語猜測。
- 例如，「Scheduler → Worker → Redis → S3」這串名稱需要由情境和責任說明帶讀：某位使用者何時會看到什麼結果、哪些步驟負責等待／處理／保存、旁邊有哪些可觀察訊號與程式入口。這只是寫法示意；實際說明必須依目標程式碼儲存庫查證。
- 程式路徑只列理解核心流程、規則、資料契約或安全維護所需的少數入口；不要逐檔加註、抄錄目錄樹，或在程式碼旁新增只為交接而存在的註解。把原因和影響寫在交接頁，再連到精確來源。
- 中大型專案要讓入口頁帶讀者走向實際存在的細節頁。依 domain、主要流程、架構責任、日常維護等讀者問題拆分；避免把每個模組各做一頁，或留下只有標題、沒有解答的空頁。
- 圖、文字、操作步驟和證據連結需互相吻合。圖說要帶讀主要路徑；圖片提供替代文字或等效說明；寬表只用於確實需要逐項比較的資訊。
- 交接指南說明系統如何服務人、接手者怎麼開始和去哪裡求助；具體操作步驟由正式維運操作手冊（runbook）承載。交接指南也不代表即時監控或正式環境驗證。未知處保留目前已知內容，寫明影響、確認來源和確認前的安全做法。
- 不放憑證、個資或秘密；存取需求連到核准申請途徑。

## 依工作需要讀取的資源

- 撰寫完整指南、整理業務知識或改善白話主線時，讀[交接方法](references/handover-method.md)。
- 設計系統脈絡／架構總覽時，讀[架構總覽指南](references/architecture-overview.md)。
- 選擇流程、狀態、序列、部署等圖型時，讀[圖型選擇與繪製手冊](references/diagram-selection.md)。
- 需要完整繪圖流程、語義模式、版型目錄、視覺品質規則或 Notion／Markdown 筆記平台交付時，讀[工程交接圖解設計與筆記平台交付指南](references/diagram-design-integration.md)。
- 編排長文件、改善閱讀節奏或檢查版面時，讀[視覺與文件設計指南](references/visual-document-design.md)；挑選真實情境、診斷或變更影響等說明方式時，讀[交接呈現模式庫](references/presentation-pattern-library.md)。
- 需要起草文件時，複製[交接範本](assets/handover-template.md)，先完成範圍與完整度盤點；只在盤點為不適用或由正式文件承接後才移除範本章節，再用程式碼儲存庫證據取代所有提示文字。

## 使用範例

- 「請依這個程式碼儲存庫的證據寫一份新維護者上手指南。從使用者遇到的問題開始，帶我走過一條真實流程，再連到規則、程式位置、觀察訊號和安全的第一步。」
- 「請檢查這份交接文件，找出不熟悉系統的人會卡住的地方；把程式架構說明改成能回答實際任務的白話解說，保留證據和未知事項。」
- 「請先盤點這個系統的接手範圍，再依完整交接門檻交付可開啟的 Markdown 文件與索引。每項適用主題都要有正文、可用正式文件、明確待確認項目或有理由的不適用標記；若內容太長，拆成互相連結的頁面繼續完成，不要只給短摘要。最後列出覆蓋狀態和尚未走讀的項目。」
- 「這是中大型 repo。請先調研一條能說清楚系統價值的主線，整理共同證據和文件大綱，再為可獨立頁面寫好分工合約並派給 subagent；最後由主編核對內容、統一架構與用詞，完成有實際頁面連結的 `index.md`。」
- 「請以指定 commit 為交接證據基線，寫給沒有本專案或業務背景的人。先說明 domain、系統核心和一條端到端情境；中大型內容請交付入口索引和有實質內容的連結頁，不要逐檔加註或提及未提交檔案。」
- 「請用一個真實例子說明資料怎麼變成報表，搭配適合的流程圖、短例子和程式入口；不要把程式碼儲存庫中的目錄逐一改寫成正文。」
- 「這份交接要放進 Notion。請交付可匯入的 Markdown、可直接上傳的架構圖圖片和可編輯圖源，並告訴我應放在哪個段落；不要只交一個 HTML 頁面。」
- 「請用讀者看得懂的方式說明故障第一步和升級邊界，並確認所有正式操作都連到已驗證的維運操作手冊。」
