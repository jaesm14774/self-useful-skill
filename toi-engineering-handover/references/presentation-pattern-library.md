# 交接呈現模式庫

這份模式庫讓維護者能用簡單名稱挑選合適的閱讀介面。它借鏡 [Motion Prompt](https://showheyohtaki.github.io/motion-prompt/) 的溝通方式：每個模式有名稱、可快速掃描的預覽、白話用途和可直接提出的需求；多個模式可以一起選，也可以附上一句偏好。此處的模式專為工程交接設計，內容仍須由目標程式碼儲存庫、文件或明確標示的推論支撐。

## 快速挑選

| 模式 | 讀者想回答的問題 | 主要呈現 |
| --- | --- | --- |
| 接手起點（Reader Launchpad） | 這系統做什麼？我先從哪件事開始？ | 一句話目的、範圍、文件狀態、安全第一步和任務入口 |
| 責任地圖（Responsibility Map） | 系統和外部服務如何分工？ | 使用者、系統邊界、主要責任、資料存放和依賴 |
| 一筆真實情境（Journey Strip） | 一個請求或資料如何走到結果？ | 依時間排序的步驟、業務規則、元件、狀態、證據 |
| 條件分路（Decision Fork） | 某個條件如何改變系統或維護者動作？ | 判斷條件、各分支、結果與下一步 |
| 狀態生命線（Lifecycle Rail） | 物件或工作有哪些狀態，如何轉換？ | 狀態、觸發、前提、終態與不合法轉換 |
| 故障診斷路徑（Diagnostic Route） | 出現症狀時先看什麼、怎麼安全處理？ | 症狀、訊號、分辨方法、核准動作、復原或升級 |
| 變更影響鏈（Change Impact Chain） | 改這裡會影響誰，怎麼確認？ | 變更點、契約、相依者、使用者結果、驗證／復原 |
| 證據卡（Evidence Card） | 這句話有何依據，可信範圍到哪？ | 主張、事實／推論／未知標籤、來源、環境／版本／日期 |
| 畫面導覽（Screen Walkthrough） | 在某個真實介面要去哪裡看或做什麼？ | 有標註的截圖、操作順序、預期訊號和適用版本 |

完整交接通常先用既有要求中的「責任地圖」與「一筆真實情境」建立心智模型。其他模式按接手者的具體任務挑選；不用為了填滿清單而全部加入。

## 模式細節

### 接手起點（Reader Launchpad）

**用途：** 新維護者首次打開文件，想快速決定閱讀方向。

```text
系統做什麼？ 一句白話目的       負責角色 · 範圍 · 最後核對版本／日期
我現在要…   [追一筆資料] [開始維護] [排查症狀]
先安全地…   [第一個低風險動作] → [成功時的可觀察訊號]
```

**資料需求：** 讀者角色、系統目的和邊界、經驗證的入口任務、預期訊號、文件驗證資訊。每個任務入口需連到相應章節。

**版面提示：** 桌機可將任務入口排成兩到三欄；窄視窗改成單欄。不要把未知的負責人、版本或成功指標填成看似正式的狀態。

### 責任地圖（Responsibility Map）

**用途：** 接手者需要看懂系統範圍、角色和主要依賴。

```text
使用者／上游 → [本系統：入口 → 核心責任 → 狀態／資料] → 下游／外部服務
                         └──── 重要信任或責任邊界 ────┘
```

**資料需求：** 可證明的元件責任、主要交換物、資料存放、系統邊界和外部互動。圖旁說明一條主要路徑、重要例外及對應程式入口。

**版面提示：** 用分組、方向和少量標記建立層次；每條線都標出交換的資訊或觸發原因。超過同一讀者問題可理解的節點量時，拆成總覽與細節圖。

### 一筆真實情境（Journey Strip）

**用途：** 接手者要沿一筆真實請求、批次或資料記錄追到完成／失敗。

```text
觸發／輸入 → 業務判斷 → 責任元件 → 狀態／結果 → 觀察訊號與下一步
    證據         證據          證據         證據              證據
```

**資料需求：** 每一步的真實條件、規則原因、實際元件、狀態改變、可觀察結果和會改變下一步的例外。來源連結要貼近對應步驟。

**版面提示：** 步驟少時用橫向流程；手機或窄頁改成縱向時間線。例外可用第二條支線表示，不要把每個罕見錯誤都塞進主路徑。

### 條件分路（Decision Fork）

**用途：** 某個條件會改變業務結果、資料狀態或維護者應採取的動作。

```text
                ┌─ 條件成立 → 結果／責任者／確認訊號
條件與證據 → 判斷
                └─ 條件不成立 → 結果／安全下一步／升級入口
```

**資料需求：** 明確的判斷條件、分支結果、負責元件或角色、每個結果如何確認。只呈現會改變結果或動作的分支。

**版面提示：** 分支文字直接寫「符合／不符合」或實際條件，不只用「是／否」。若分支很長，拆出獨立任務路徑並彼此連結。

### 狀態生命線（Lifecycle Rail）

**用途：** 接手者需要掌握實體、請求或工作從建立到終結的生命週期。

```text
[狀態 A] ──事件／前提──> [狀態 B] ──事件／前提──> [終態]
       ↘ 失敗或重試入口                   × 禁止或不存在的轉換
```

**資料需求：** 狀態的業務含義、產生轉換的事件、守門條件、終態、重試／取消／補償行為，以及實際儲存位置。只有能從程式或權威規格確認的轉換才畫實線；未確認項目另行標記。

### 故障診斷路徑（Diagnostic Route）

**用途：** 新維護者看見症狀後，需要知道第一個觀察點和安全的升級界線。

```text
症狀 → 先看訊號 → 區分候選原因 → 核准的安全動作 → 恢復證據／停止並升級
```

**資料需求：** 症狀的範圍、正式訊號入口、可分辨原因的條件、已核准的操作手冊和恢復訊號。沒有已驗證的正式步驟時，清楚連結 runbook 或標為待確認，不創造命令。

**版面提示：** 把停止條件、資料風險或需核准的步驟做成醒目的文字提示；不能只用紅／綠色區分，也不要把核准條件藏在折疊內容中。

### 變更影響鏈（Change Impact Chain）

**用途：** 維護者要評估一項程式、設定或資料契約變更會波及哪裡。

```text
欲修改處 → 規則／契約 → 直接相依者 → 使用者或資料結果 → 驗證／回復
```

**資料需求：** 變更點、上游／下游、API 或 schema 契約、歷史資料影響、已有檢查、核准的回復方式與責任角色。未知相依處寫成待查，不以目錄名稱猜測。

### 證據卡（Evidence Card）

**用途：** 關鍵說法需要一眼看出證據和可適用的範圍。

```text
主張： [這個版本中可確認的行為]
狀態： [已觀察事實 / 由程式推論 / 待確認]
來源： [可點回的檔案、符號或正式記錄]
範圍： [commit／版本、環境、日期]　下一步：[如何補足證據]
```

**版面提示：** 標籤文字與樣式並用，不靠顏色單獨傳達事實／推論／未知。近端連結可用於短證據；大段規格引用改用連結和精確章節，不貼入冗長摘錄。

### 畫面導覽（Screen Walkthrough）

**用途：** 接手者需要定位真實管理介面、儀表板、設定頁或告警畫面。

```text
[適用環境／版本的截圖，標註 1 → 2 → 3]
1 從哪裡進入 → 2 看哪個欄位／訊號 → 3 如何確認或安全離開
```

**資料需求：** 畫面的真實來源、適用版本／環境、操作入口、預期訊號、權限邊界和畫面失效時的替代查詢方式。遮蔽秘密與個人資料；舊截圖需標示可能漂移的位置。

## 格式與互動選擇

- **Markdown／Word：** 用標題層級、可點擊目錄、短段落、可渲染的圖和靠近主張的來源連結建立導航。圖片提供替代文字或等效說明；先確認目標平台支援 Mermaid，否則輸出並嵌入可讀圖像。
- **HTML／網站：** 僅在使用者提出、儲存庫已有發佈慣例，或互動明確能解決尋路任務時採用。優先做搜尋／章節跳轉、角色入口、圖形放大等實際操作；核心知識在沒有 JavaScript 時仍可讀取。檢查鍵盤、窄螢幕、列印和減少動態效果模式。
- **投影片：** 依閱讀／簡報順序安排單一問題和單一視覺焦點；講者備註保存證據、條件和例外，不能讓簡報版面迫使細節消失。
- **動畫：** 只用來顯示真的有先後、生命週期或逐步揭露價值的內容。預設由讀者控制播放，不自動循環；另提供靜態圖和文字路徑。

## 如何使用模式名稱

如果讀者已選模式或附上備註，遵照選取範圍與目的，並把備註當成設計約束。讀者沒有指定時，根據實際接手任務挑選最少的一組模式，不必先讓他學圖表術語。

可直接提出這類要求：

- 「先做《接手起點》，讓值班人員知道能安全查看什麼。」
- 「用《一筆真實情境》追一筆資料，再用《條件分路》說明何時重試。」
- 「把《變更影響鏈》放在修改指南旁；只保留有程式或設定證據的連線。」
- 「給我三種《故障診斷路徑》的小型版面預覽，我選好後再套用到這個系統。」

若提供可選模式的預覽，每個選項一併列出白話用途、所需證據和適用章節；讀者選定後只套用選取項目。模式是溝通詞彙和版面起點，不可取代程式碼儲存庫查證、圖型選擇或目標格式渲染驗收。
