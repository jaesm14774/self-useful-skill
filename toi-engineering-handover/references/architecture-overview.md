# 架構總覽：用一張圖交代完整責任與路徑

本指南供完整 TOI 的系統脈絡／架構總覽使用。目標是一張在正常閱讀尺寸下能快速定位、事實可追溯的圖：讓新維護者看出系統邊界、入口、主要責任、持久狀態，以及真正影響維護的外部或非同步路徑。完整是相對於圖上宣告的範圍；不代表逐一畫出每個 class、function、endpoint、table 或部署副本。

## 先決定這張圖的範圍

先用一句話寫出讀者看完要能回答的問題，再選定一致的抽象層次：

- 系統脈絡：誰使用本系統、哪些外部系統提供輸入或消費結果。
- 服務／容器架構：主要執行單元各自負責什麼，如何交換資料，以及狀態保存在哪裡。
- 部署／信任拓樸：已知服務實際部署在哪些環境、網路或安全邊界，哪些團隊負責。

一張圖可以呈現外部角色與本系統主要服務，但不要把服務、程式函式、資料欄位、團隊和雲端資源混在同一層。若讀者要同時理解業務全貌、請求時序和實際部署，保留一張高層總覽，再加上各自回答明確問題的流程、序列或部署圖。

完整交接的系統總覽通常要檢查以下元素是否在範圍內：使用者或上游來源、入口、核心處理、主要資料來源或持久化、佇列與消費者、外部副作用，以及會改變路徑的身份／信任邊界。沒有的元件不要補上；不確定的責任、連線或部署位置標為待確認，不能用常見架構慣例代替證據。

## 用責任壓縮，而不是刪掉關係

一張總覽以約 6–12 個主要元件作為起點；很小的系統可以更少。元件代表穩定且可命名的責任或獨立邊界，不代表程式碼清單。

- 多個副本只有在角色、介面、信任區和故障行為都相同，且副本差異與交接問題無關時才合併。
- 資料庫、快取、佇列、worker、身份供應商和外部服務若有不同的責任、資料保證、owner 或故障模式，就分開呈現。
- 不要把「所有 backend」塞成一個無法追責的方塊；也不要為了看起來完整而把每個模組都列成節點。
- 方塊以短名稱表示角色；副標補一個必要的實作名稱或技術；owner、環境等資訊只在它會影響接手行動時才標示。
- 區域、網路、信任區或團隊邊界只依已確認事實繪製。群組只表示包含或共同歸屬，不代表群組內元件彼此都有連線。

若完整的範圍無法在可讀尺寸下呈現，先保留一張有用的高層總覽，再為過密區域補一張局部圖。不要縮小標籤、堆長句、隱藏關鍵關係到互動提示中，或合併性質不同的元件來湊進單張圖。

## 排成一條可追的主路徑

先把最重要的請求或資料路徑排成單一方向，常見順序為：

    使用者／來源 → 入口 → 核心服務 → 主要狀態或結果

再從實際起點接出少量支線：

- 非同步工作沿著「產生者 → queue／event bus → worker → 外部副作用」完整畫出。標示事件或工作名稱；需要時說明持久化或消費語意。
- Cache、身份服務和觀測系統放在實際使用它們的元件附近；只有當它們能解釋重要行為或維護動作時才加入。
- 上游、下游、外部服務和本系統邊界位置要明確；不要讓一條線穿過圖面，迫使讀者猜測端點或責任歸屬。
- 同一張圖不要用一組箭頭同時表達靜態相依、逐步呼叫順序和資料生命週期。時序、重試、補償與狀態轉換各自用能回答問題的圖型。

每條箭頭都要能用一句話說明。方向、資料／事件名稱、呼叫或依賴關係，以及會改變理解的同步／非同步差異要明確。顏色、虛線或動畫只能輔助語意，不可成為理解關係的唯一依據。

## 讓全貌在靜止畫面就成立

Live-panel 的可移植優點是整張拓樸固定、任何一幀都保有完整脈絡，動態只用來呈現狀態或資料流，而且畫面上的提示彼此一致。[原始 skill](https://github.com/ythx-101/live-panel-skill/blob/main/SKILL.md) [motion grammar](https://github.com/ythx-101/live-panel-skill/blob/main/references/motion-grammar.md)

用在工程交接時，先把這個規則套在靜態圖：讀者不需要看動畫、點擊節點、打開圖例、展開卡片或閱讀一大段圖說，才知道主要元件和路徑。若使用互動式圖，概覽仍要完整；互動只用來追蹤、聚焦或補充證據。若使用動畫或影片，第一幀就呈現完整圖，移動只能強調已驗證的路徑或狀態。沒有來源的計數或效能值必須標示為示意。

若重製特定作者的圖，先確認授權並保留必要署名；一般情況只移植清楚的構圖原則，不複製其圖稿、配色細節或專屬視覺設計。

## 完稿檢查

先對照 repository、規格或 owner 確認主要節點與連線，再看目標文件的實際渲染。縮到文件正常閱讀尺寸時，讀者應能在幾秒內指出：

1. 本系統的邊界、主要使用者或來源，以及入口。
2. 核心責任如何串接，主要狀態存在哪裡。
3. 哪些非同步或外部路徑會影響結果、責任或故障處理。

再確認沒有孤立且未解釋的節點、箭頭方向含糊、關鍵關係只靠顏色、文字被縮得太小或路徑交叉到無法追讀。圖說應用白話帶讀一條主路徑，指出會改變維護動作的支線，並連回實際程式、設定或規格。若看圖仍要先猜系統如何運作，先修正範圍和拓樸，再調整視覺樣式。
